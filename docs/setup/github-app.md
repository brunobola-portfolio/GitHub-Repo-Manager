# GitHub App Identity (for AI Deep Review)

> **Status: Roadmap.** This guide describes the planned setup for the GitHub
> App identity slice of AI Deep Review. The current implementation publishes
> AI reviews under the OAuth user's identity with a clear
> `> 🤖 Generated by GitHub Repo Manager` footer in the review body. When the
> identity slice ships, switching to a `github-repo-manager[bot]` author will
> be a runtime config change — no code change needed in your fork.

---

## What this enables

By default, AI Deep Review publishes the batched GitHub review through the
authenticated user's OAuth token. The review shows up under that user's
avatar with a footer disclosing that the content was AI-generated. That works
well for individuals but has three downsides for organisations:

- **Attribution is misleading at a glance** — teammates see "Alice approved
  this PR" before they spot the footer.
- **Required-reviewer rules don't see it as a bot** — if your branch
  protection requires "1 approval from a human reviewer", an AI-generated
  approval still counts.
- **Per-installation scoping is impossible** — a user must be a member of
  every org whose PRs they want reviewed.

A registered GitHub App fixes all three:

- Reviews appear under `github-repo-manager[bot]` with the bot badge.
- Branch protection can be configured to ignore bot reviews for the
  human-approval count.
- Org admins install the App once; every member of the org can use AI Deep
  Review on any repo without exposing their personal token.

---

## Prerequisites

- **Admin access** to the GitHub organisation or user account that will own
  the App.
- A reachable webhook URL (HTTPS in production; `ngrok` or similar for local
  dev).
- The `WEBHOOK_SECRET` value already present in your `.env` (used for HMAC
  signature verification on inbound deliveries).

## Step-by-step registration

1. Sign in to GitHub and open
   **Settings → Developer settings → GitHub Apps → New GitHub App**.
2. Fill in the app metadata:
   - **GitHub App name:** `GitHub Repo Manager` (must be globally unique;
     append your org if taken).
   - **Homepage URL:** the public URL of your deployment (e.g.
     `https://repo-manager.example.com`).
   - **Callback URL:** `https://<your-domain>/api/auth/github-app/callback`.
     For local development:
     `http://localhost:3001/api/auth/github-app/callback`.
   - **Setup URL (optional):** the same domain root — GitHub redirects users
     here after they install the App on a new org.
   - **Webhook URL:** `https://<your-domain>/api/v1/webhooks/github`
     (the existing event-ingestion endpoint; see
     [`docs/event-ingestion.md`](../event-ingestion.md)).
   - **Webhook secret:** paste the same value as `WEBHOOK_SECRET` from your
     `.env`. The server verifies every delivery via the
     `X-Hub-Signature-256` header.
3. Set repository permissions:

   | Permission | Access | Why |
   | --- | --- | --- |
   | Pull requests | Read & write | Post the batched review, update PR body for `/describe` |
   | Contents | Read-only | Fetch file diffs and `.repomanager/review-rules.md` |
   | Issues | Read-only | Surface linked-issue context in walkthroughs |
   | Metadata | Read-only | Required by GitHub on every App |

4. Set organisation permissions:

   | Permission | Access | Why |
   | --- | --- | --- |
   | Members | Read-only | Resolve org-shared Prompt Studio presets to org members only |

5. Subscribe to events: `Pull request`, `Pull request review`,
   `Pull request review comment`, `Push`. (Same set the existing
   webhook ingester already handles.)
6. Choose **Where can this GitHub App be installed?** — typically
   **Only on this account** for self-hosts, or **Any account** if you offer
   it as a SaaS multi-tenant service.
7. Click **Create GitHub App**.

After creation, on the App's settings page:

- Note the **App ID** (shown at the top of the page).
- Note the **Client ID** (same page, "About" section).
- Click **Generate a new client secret** — copy it immediately, you cannot
  view it again later.
- Scroll to **Private keys** and click **Generate a private key**. Your
  browser downloads a `.pem` file. Store this securely — it cannot be
  retrieved later, only regenerated.

Then, on the same page, click **Install App** in the left sidebar and
install the App on the org or repos you want it to review. GitHub redirects
you back through the Setup URL.

## Environment variables

Add the following to your `.env`. Placeholders below correspond to the
values captured during registration.

```env
# GitHub App identity (planned — not yet wired into deep-review.js)
GITHUB_APP_ID=123456
GITHUB_APP_CLIENT_ID=Iv1.0000000000000000
GITHUB_APP_CLIENT_SECRET=<client secret from "Generate a new client secret">
GITHUB_APP_PRIVATE_KEY_PEM="-----BEGIN RSA PRIVATE KEY-----
<paste full PEM body, including newlines, between the BEGIN/END markers>
-----END RSA PRIVATE KEY-----"

# Optional — only needed if you want to lock the App to one installation
# (single-tenant deploys). When omitted, the server resolves the right
# installation per-request via the `pull_request.installation.id` field.
GITHUB_APP_INSTALLATION_ID=98765432
```

> **PEM formatting on Windows / docker-compose.** A multi-line value inside
> double quotes works in `dotenv` but not in every PowerShell or docker
> wrapper. The safest portable form is to base64-encode the PEM and decode
> it inside the server. The roadmap implementation will accept both
> `GITHUB_APP_PRIVATE_KEY_PEM` and `GITHUB_APP_PRIVATE_KEY_PEM_BASE64`.

## Testing the integration

Once the implementation lands and the env vars are set:

1. Restart the server (`npm run dev:server`).
2. Visit any PR in the app and click **Generate AI Review**.
3. Click **Publish to GitHub** in the review draft.
4. Open the same PR on github.com — the new review row should now show
   `github-repo-manager[bot]` as the author with the **bot** badge, instead
   of your personal avatar.

If the bot identity does not appear, the server falls back to the OAuth
user identity automatically and logs a structured warning at level `warn`
with `{ feature: 'pr-deep-review-publish', identityFallback: true }`. Check
your application logs.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `401 Unauthorized` on publish | Wrong PEM, or PEM without trailing newline | Regenerate the private key on GitHub, paste fresh; verify `BEGIN`/`END` markers are intact |
| `404 Not Found` on publish | App is not installed on the target repo's org | Install the App on the target org (Settings → Integrations → GitHub Apps → Configure) |
| `403 Resource not accessible by integration` | Missing **Pull requests: write** permission | Edit the App, update permissions, and accept the new permissions on every installation |
| Org-shared prompts not resolving | Missing **Organization members: read** | Same as above — re-accept the permission upgrade |
| Identity fallback in logs | `GITHUB_APP_INSTALLATION_ID` set but stale (org reinstalled) | Remove the env var; the server will resolve per-request from the webhook payload |

## Why we ship this as roadmap, not vaporware

The OAuth-user publish path is the entire MVP we needed for AI Deep Review
to be useful. The bot identity is purely a polish layer — every contract
(batched review, idempotency key, footer disclosure) is already correct
under OAuth, so the eventual GitHub App swap is mechanical: replace the
authenticator the publish helper uses, keep the payload shape identical.
We document the planned setup now so operators who care about bot identity
can prepare their App registration today and flip the switch on day one.
