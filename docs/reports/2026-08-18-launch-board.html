Diffs de PR chegam aos fornecedores de IA sem redaçãoa decidir

secret-redactor.js existe e funciona, mas só está ligado ao repo-context-builder.js. As três funcionalidades que enviam diffs — pr-deep-review, pr-chat, pr-review — não o chamam. Um PR que acrescente um .env ou uma chave escrita à mão envia essa linha tal e qual.

Porque não o corrigi já: a regex atual apanha nomes de identificadores (token, secret, password), o que num diff de revisão apagaria metade das linhas e tornaria a funcionalidade inútil. O que isto precisa é de padrões com a forma do valor — sk-, ghp_, github_pat_, chaves AWS, atribuições de alta entropia. É meia hora de trabalho, mas é uma decisão sobre falsos positivos, não uma correção óbvia.

Segredo de webhook único para toda a instânciasó em SaaS

Em auto-alojamento está correto: o operador é o dono da instância. Em multi-inquilino, cada cliente configuraria o mesmo segredo no seu GitHub, e portanto poderia assinar eventos para repositórios de outro. O isolamento do Work Board que fechei no PR #328 limita o que daí se vê, mas a escrita de eventos falsos continua possível.

Só morde se abrires o SaaS multi-inquilino. Com DEPLOYMENT_MODE=self-host — o que vais lançar — não se aplica. A correção é uma coluna por inquilino e um fluxo de rotação, não um patch.

O que fazes a seguir

A v4.21.0 saiu — fecha o painel de nove lentes; os dois repositórios estão no main, sem PRs abertos. Sobra isto, por esta ordem. Os três primeiros são no servidor e a ordem é obrigatória: o certificado tem de existir antes de forçares o redirect, ou reencaminhas para um endereço que ainda não serve TLS.

  1. Instalar o ARR no IIS

    Application Request Routing mais URL Rewrite. Sem o ARR, o IIS não faz proxy reverso para o Node em 127.0.0.1:3001 e o site fica no ar sem aplicação por trás.

  2. Emitir o certificado para repomanager.bolalabs.pt

    Já agora, o mesmo para arcva.pt: o certificado atual só cobre www.arcva.pt, por isso https://arcva.pt dá aviso de segurança no browser e http:// não redireciona. O site já linka www para se proteger; reemitir com os dois nomes e um redirect apex→www fecha isso de vez.

    Segue as nove secções do guia em docs/guides/deploy-iis-windows.md.

    O redirect HTTP→HTTPS vai depois do certificado, nunca antes. Ao contrário ficas com um site que reencaminha para um endereço que ainda não serve TLS.
  3. Correr deploy/iis/deploy.ps1 -FromRelease latest

    Verifica o SHA-256, recusa artefactos mal rotulados, faz uma cópia de segurança, confirma a versão que acabou de instalar e reverte sozinho se a verificação de saúde falhar. Experimenta primeiro com -DryRun, que não precisa de elevação.

  4. Pôr REPOMANAGER_IS_LIVE = true

    Em src/site.ts no repo do site. É a última coisa, depois de confirmares que o domínio serve mesmo a aplicação. Um booleano — o menu, o contador da Home e os dois botões «Abrir a app» seguem-no todos.
