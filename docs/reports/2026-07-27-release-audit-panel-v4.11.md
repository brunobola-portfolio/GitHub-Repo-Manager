## BLOCKER (7)

### 1. Refunded/disputed subscriptions reopen the double-charge path that the 409 guard was added to close

- **Ficheiro:** `server/routes/billing.js:14`
- **Evidência:** `const ACTIVE_SUB_STATUSES = new Set(['active', 'trialing', 'past_due', 'incomplete']);` — the guard at billing.js:78 (`if (sub?.stripe_subscription_id && ACTIVE_SUB_STATUSES.has(sub.status))`) is the only thing preventing a second Stripe subscription. The refund/dispute handlers added this session write two NEW statuses that are not in that set: server/routes/stripe-webhooks.js:237 `const nextStatus = event.type === 'charge.refunded' ? 'refunded' : 'disputed';` and stripe-webhooks.js:262-265 `UPDATE user_subscriptions SET tier = 'free', status = ?`. Grep confirms 'refunded'/'disputed' appear nowhere else in server/ — billing.js has never been taught about them. Crucially, a refund/dispute does NOT cancel the subscription in Stripe (the handler's own comment at stripe-webhooks.js:227 says so), so the first subscription is still live and billing.
- **Cenário de falha:** Pro customer on a $19/mo subscription; support issues a partial refund (or the customer files a chargeback). Webhook sets tier='free', status='refunded'. The user's UI now shows Free, so they click Upgrade → POST /api/v1/billing/checkout. `sub.status` is 'refunded', which is not in ACTIVE_SUB_STATUSES, so the 409 `subscription_exists` guard does not fire and a SECOND Stripe subscription is created against the same customer. The customer is now billed $38/mo. Worse, the `ON CONFLICT(user_id) DO UPDATE SET ... stripe_subscription_id = ?` at stripe-webhooks.js:159-161 overwrites the row with the new subscription id, orphaning the first one — it keeps billing forever with nothing in the DB pointing at it, which is verbatim the scenario billing.js:73-77 documents as the reason the guard exists.
- **Correcção sugerida:** Add 'refunded' and 'disputed' to ACTIVE_SUB_STATUSES — both mean "the Stripe subscription still exists and will keep billing", which is exactly the predicate the set encodes. The checkout route should return the same 409 and point the user at the billing portal; a refunded customer who genuinely wants to restart should cancel first (which yields status='cancelled' via customer.subscription.deleted, correctly allowing a new checkout).

### 5. O tray residente nunca e parado durante o self-update instalado — o update aborta e o servidor nao volta

- **Ficheiro:** `packaging/windows/installer.iss:527`
- **Evidência:** `PrepareToInstall` comeca com `Result := ''; if not IsAppRunning() then exit;` (installer.iss:526-527). `StopTrayIfRunning()` so e alcancavel a partir de `TryStopRunningApp()` (installer.iss:479), que so e chamado DEPOIS desse gate. O proprio comentario em installer.iss:430-432 declara a consequencia: «It holds a lock on {app}\GitHub Repo Manager.exe (which would block the [Files] replace and leave the update aborted with no server running)». `IsAppRunning()` (installer.iss:246-272) depende de `<data>\.grm.pid` + `tasklist` confirmar um node.exe vivo — e nada no servidor escreve/remove esse pidfile (grep por `.grm.pid` em server/ e scripts/ nao devolve nada; so start.ps1:354 escreve e stop.ps1:79 apaga). O handoff do update (server/lib/updater.js:346-352) faz spawn de `setup.exe /VERYSILENT /SUPPRESSMSGBOXES /UPDATED=1` e depois `setTimeout(() => requestShutdownImpl('update'), 500)` (updater.js:375) — ou seja, o servidor mata-se a si proprio enquanto o setup arranca. Em cascata: mesmo que o [Files] passasse, o relaunch `[Run] ... Parameters: "--no-browser"; Check: IsUpdatedMode` (installer.iss:175) cai no mutex de instancia unica do tray (Launcher.cs:140-151), que com `noBrowser=true` faz `return 0` sem arrancar servidor nenhum.
- **Cenário de falha:** Instalacao via installer, lancada normalmente (tray residente — o caminho por omissao). Utilizador clica Settings -> About -> «Update now». updater.js faz spawn do setup.exe e 500 ms depois pede shutdown. Quando o setup chega a PrepareToInstall (tipicamente <1 s em /VERYSILENT), o node ja saiu: o `.grm.pid` fica com um PID morto, `tasklist` nao confirma, `IsAppRunning()` devolve False, `PrepareToInstall` sai imediatamente e `StopTrayIfRunning()` nunca corre. O tray continua residente e mantem `{app}\GitHub Repo Manager.exe` bloqueado -> o passo [Files] falha com sharing violation e, sob /SUPPRESSMSGBOXES, a resposta por omissao a Abort/Retry/Ignore e Abort -> o setup aborta. O servidor ja foi desligado e nada o volta a arrancar (o [Run] /UPDATED nem chega a correr; e se chegasse, o mutex do tray fazia-o no-op). O utilizador fica com um icone de tray a dizer «○ Not responding», sem mensagem, e docs/windows.md:184-187 diz explicitamente que «Installed builds have no automatic rollback» — recuperacao so por reinstalacao manual. O mesmo estado ocorre de forma deterministica quando o utilizador corre setup.exe a mao depois de o node ter crashado com o tray ainda vivo.
- **Correcção sugerida:** Chamar `StopTrayIfRunning()` incondicionalmente em `PrepareToInstall` (e em `CurUninstallStepChanged`) antes do gate `IsAppRunning()` — o tray e um processo independente do servidor e o seu lock sobre o exe e o que bloqueia [Files], quer o node esteja vivo ou nao. Alternativamente, mover a paragem do tray para dentro do proprio handoff (server/lib/updater.js), antes de fazer spawn do setup.exe.

### 6. Utilizador BYOK é informado "AI is not configured" — /config/ai-status ignora a chave do próprio utilizador

- **Ficheiro:** `server/routes/ai/core.js:88`
- **Evidência:** `const configured = !!process.env.GEMINI_API_KEY || !!aiService.model;` e, se falso, `return res.json({ configured: false, ... })` na linha 90 — antes de qualquer leitura de `req.session.userId` ou `req.getAIProvider`. `aiService` só é inicializado a partir do env (`server/index.js:123-125`, `await aiService.initialize(config.geminiApiKey)`), nunca de chaves de utilizador. Verificado em runtime: servidor arrancado com `GEMINI_API_KEY=` vazia devolve `{"configured":false,"provider":null,"keyHealth":"unknown","lastCheckedAt":null}`. O cliente trata isso como facto: `src/api/aiFetch.js:201-203` lança `AINotConfiguredError` ("AI is not configured. Set up a provider in Settings → AI Configuration.") SEM chegar a fazer o pedido, e `src/api/ai.js` (`withAIConfigured`) devolve placeholders com "Connect an AI provider in Settings → AI Configuration to see real analysis." O `.env.example:106-111` documenta explicitamente esta configuração como a recomendada: "The server-side GEMINI_API_KEY below is an OPTIONAL fallback... Leave empty in multi-tenant deployments".
- **Cenário de falha:** Deployment BYOK-puro (sem `GEMINI_API_KEY` e sem chave para o `AI_PROVIDER` do servidor — o cenário que o .env.example recomenda). O utilizador guarda a sua chave Anthropic em Settings → AI Configuration; o registo fica em DB e `createProviderForUser` resolveria a chave corretamente. Mas `/config/ai-status` devolve `configured:false`, portanto AttentionFeed, InboxPanel, translate-search e narrativas nunca chegam a fazer o pedido e mostram "AI is not configured. Set up a provider in Settings → AI Configuration" — a apontar para o ecrã onde a chave já está. As superfícies de `api/ai.js` mostram cartões de placeholder "Connect an AI provider…". A mensagem culpa o utilizador por uma configuração que ele já fez, e o estado fica em cache 60 s (`src/api/aiStatus.js:3`).
- **Correcção sugerida:** Em `/config/ai-status`, resolver o provider do utilizador antes de decidir `configured`: mover o early-return para depois de `resolveProvider(feature)` e considerar `configured = !!(serverKey || userProvider)`. Enquanto isso, `aiFetch` não deve pré-emptir com `AINotConfiguredError` quando o status é apenas "desconhecido".

### 7. Todas as mutações de AI via utils/aiFetch omitem o header CSRF — feature morre com "Something went wrong" e um Retry que nunca pode funcionar

- **Ficheiro:** `src/utils/aiFetch.js:33`
- **Evidência:** `fetchJSON` monta `headers: { 'Content-Type': 'application/json', ...(options.headers || {}) }` e nunca chama `getCsrfToken()`. Os callers passam apenas `{ method, body }`: `src/hooks/useAIDeepReview.js:81` (POST generate), `:105` e `:127` (PATCH dismiss/edit), `:150` (POST publish), `:173` (DELETE discard); `src/hooks/usePRCommand.js:84,108,123`; `src/hooks/usePromptStudio.js:90,102,114,123,147`. O servidor aplica CSRF globalmente: `server/index.js:324` `app.use('/api/', requireCsrfToken)` e `/api/ai/*` não está na bypass list (`server/middleware/csrf.js:40-45`). Verificado em runtime contra o servidor real: `POST /api/ai/deep-review/o/r/1` sem header devolve `HTTP/1.1 403` com corpo `{"error":"Invalid CSRF token","code":"csrf_invalid"}`. O código `csrf_invalid` não existe em `KNOWN_ERRORS` nem em `CODE_ALIASES` (`src/utils/errors.js:104-359`), o status 403 não é 401, e `pickRawMessage` não encontra "quota"/"rate limit" — logo `formatUserError` cai no `FALLBACK` (`errors.js:305-309`): "Something went wrong / Please try again. If the problem persists, contact bruno@bolalabs.pt." com ação `retry`. Ao contrário de `apiFetch` (`src/utils/api.js:401-406`), `fetchJSON` não invalida o token nem repete o pedido.
- **Cenário de falha:** Utilizador autenticado abre um PR, carrega em "Generate AI review". O POST sai sem `X-CSRF-Token`, o servidor devolve 403 `csrf_invalid`, e `AIReviewPanel` (`src/components/PRReview/AIDeepReview/AIReviewPanel.jsx:156-158`) mostra `AIErrorState` com "Something went wrong — Please try again" e um botão Retry ligado a `onGenerate`, que reproduz exatamente o mesmo 403 indefinidamente. Idêntico para dismiss/edit/publish/discard de comentários, PR Commands e todo o CRUD do Prompt Studio. A causa é conhecida e acionável (header em falta) e é apresentada como falha genérica. Os testes unitários não apanham porque mockam `fetch`, e o e2e não apanha porque em mock mode `generate()` faz short-circuit (`useAIDeepReview.js:69-75`).
- **Correcção sugerida:** Em `fetchJSON`, injetar `X-CSRF-Token: await getCsrfToken()` quando o método for POST/PUT/PATCH/DELETE e repetir uma vez após invalidar o token em 403 `csrf_invalid` (mesmo padrão de `src/utils/api.js:401-410`). Independentemente disso, adicionar `csrf_invalid` a `KNOWN_ERRORS` para que um 403 residual não se apresente como "Something went wrong".

## MAJOR (27)

### 1. A partial refund downgrades a fully-paying customer to Free

- **Ficheiro:** `server/routes/stripe-webhooks.js:233`
- **Evidência:** ``` case 'charge.refunded': case 'charge.dispute.created': {     const object = event.data.object;     ...     const result = db.prepare(`         UPDATE user_subscriptions SET tier = 'free', status = ?, updated_at = datetime('now')         WHERE stripe_subscription_id = ?     `).run(nextStatus, subscriptionId); ``` Nothing between line 233 and line 265 consults `object.refunded` (Stripe's boolean for "fully refunded") or compares `object.amount_refunded` against `object.amount`. Stripe emits `charge.refunded` for every refund, partial included.
- **Cenário de falha:** Operator issues a $5 goodwill credit on a $19 Pro invoice from the Stripe dashboard. Stripe sends `charge.refunded` with `amount: 1900, amount_refunded: 500, refunded: false`. The handler resolves the subscription and sets `tier='free', status='refunded'`. `getStripeTier()` (server/middleware/require-tier.js:67-70) only returns a tier for `status = 'active'`, so the customer drops to Free on the very next request — while their subscription is untouched in Stripe and they continue paying the full $19 next month. They lose every Pro headroom limit they are still paying for, with no automatic recovery.
- **Correcção sugerida:** Gate the downgrade on a full refund: `if (event.type === 'charge.refunded' && object.refunded !== true) break;` (or compare `amount_refunded >= amount`). Log the partial refund for the operator instead of acting on it. `charge.dispute.created` should stay unconditional — a dispute is always full-amount risk.

### 2. The refund/dispute downgrade is silently undone by the next customer.subscription.updated event

- **Ficheiro:** `server/routes/stripe-webhooks.js:206`
- **Evidência:** ``` case 'customer.subscription.updated': {     const sub = event.data.object;     const rawSubTier = sub.metadata?.tier || (sub.items?.data?.[0]?.price?.metadata?.tier) || 'pro';     const tier = await reconcileTierFromPrice(stripe, sub, rawSubTier, null);     db.prepare(`         UPDATE user_subscriptions SET             tier = ?, status = ?, ...         WHERE stripe_subscription_id = ?     `).run(tier, sub.status, ...); ``` This unconditionally rewrites both `tier` and `status` from the Stripe object. There is no latch recording that the subscription was refunded or charged back — grep confirms 'refunded'/'disputed' exist only inside the handler at stripe-webhooks.js:233-265 and are read by nothing.
- **Cenário de falha:** Customer files a chargeback on their Pro invoice. `charge.dispute.created` sets `tier='free', status='disputed'` — the operator is out the money plus Stripe's dispute fee. The customer then opens the billing portal (which billing.js:81 explicitly tells users to do: "Use the billing portal to change your plan") and switches plan or updates their payment method. Stripe emits `customer.subscription.updated` with `status: 'active'`; the handler writes `tier='pro', status='active'` and the charged-back customer has full paid access again, permanently, with no record that a dispute ever happened.
- **Correcção sugerida:** Persist the suspension as a separate column (e.g. `billing_hold` / `suspended_reason`) that the refund/dispute handlers set and only an explicit operator action or a `charge.dispute.closed` with `status='won'` clears. Have `customer.subscription.updated` (and `invoice.paid`, stripe-webhooks.js:294) refuse to promote `status` back to 'active' or restore `tier` while the hold is set.

### 3. A retried invoice.paid permanently loses the deferred licence key for a delayed-payment customer

- **Ficheiro:** `server/routes/stripe-webhooks.js:290`
- **Evidência:** ``` const deferred = db.prepare(     "SELECT user_id, billing_period FROM user_subscriptions WHERE stripe_subscription_id = ? AND status = 'incomplete'" ).get(invoice.subscription);  db.prepare(`UPDATE user_subscriptions SET status = 'active', ... WHERE stripe_subscription_id = ?`).run(invoice.subscription);  if (deferred?.user_id) {     const sub = await stripe.subscriptions.retrieve(invoice.subscription);   // line 300 — can throw     ...     await issueLicenseForCheckout({ ... });                                   // line 310 } ``` The `status='incomplete'` marker — the ONLY signal that this invoice owes a deferred licence — is destroyed by the UPDATE at line 294 before the two `await` calls that can fail. The outer catch (line 373) calls `forgetIdempotency()` and returns 500, which is precisely an instruction to Stripe to retry the same event.
- **Cenário de falha:** Customer pays with a delayed method (SEPA debit / Boleto). `checkout.session.completed` arrives with `payment_status='unpaid'`, so the handler parks the row as `status='incomplete'` and defers the licence (stripe-webhooks.js:133-145). Days later `invoice.paid` arrives: `deferred` is found, `status` is set to 'active', then `stripe.subscriptions.retrieve` throws on a transient network blip. The catch deletes the idempotency row and returns 500. Stripe retries the identical event; this time the SELECT finds nothing (status is now 'active', not 'incomplete'), so `deferred` is null and the whole licence-issuance block is skipped. `billing_reason` for a first invoice is 'subscription_create', not 'subscription_cycle', so the renewal-reissue block at line 339 does not cover it either. The customer has paid, holds an active paid tier in the SaaS, and never receives the licence key — and nothing logs that it was skipped.
- **Correcção sugerida:** Do not clear the deferral marker before the async work succeeds. Either move the `status='active'` UPDATE to after `issueLicenseForCheckout` resolves, or capture the deferral in a durable per-invoice ledger row (mirroring `issued_licenses`' per-session idempotency) that is only marked done once the licence is actually issued, so a retry re-reads it.

### 5. O cartão Pro da landing page vende "priority support", que é entrega exclusiva de Enterprise

O consumidor trata `tierError` como quota: `src/hooks/useAIPolish.js:153-157` faz `if (e?.status === 429 || e?.tierError) { setQuotaHit(true); updateRow(row.fullName, { status: 'quota', error: 'AI quota exceeded' }) }`.
