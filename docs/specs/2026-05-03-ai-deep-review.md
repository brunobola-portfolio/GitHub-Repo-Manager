## Goal

Ship a premium "AI Deep Review" experience that turns the existing PR Review surface into a tool devs actively choose over GitHub.com — by generating a structured walkthrough, line-level review comments with one-click code suggestions, and a Mermaid sequence diagram, then letting the user **edit, accept, or dismiss each AI comment in a draft state before publishing the whole thing to GitHub as a single batched review**.

**Success looks like:** a user opens a PR, gets a walkthrough + 5–25 inline AI comments + a per-file change table in under 15 seconds (warm cache: instant), edits or dismisses anything they disagree with, clicks **Publish to GitHub**, and teammates on github.com see a single high-quality review under the user's identity with a "Generated by GitHub Repo Manager" footer.

---

## Why this approach (B — hybrid in-app + publish)

Validated against alternatives in research dated 2026-05-03:

| Option | Verdict |
|---|---|
| A — In-app only | Premium feel but invisible to teammates not on the app. Fails the "very desired by devs" bar. |
| **B — Hybrid (chosen)** | Premium reading + editing in-app, full visibility on GitHub.com. No competitor OSS tool does both. |
| C — GitHub App only | Mature pattern (CodeRabbit) but commodifies the product into "another bot" and loses the premium UI moat. |
| D — Embed PR-Agent OSS | AGPL-3.0 contamination of the whole product; Python sidecar in a Node app; not designed as a library. |

Validated GitHub primitives (research 2026-05-03):
- `POST /repos/{o}/{r}/pulls/{n}/reviews` accepts `body` + `comments[]` in **one batched call** (avoids secondary rate limits)
- ` ```suggestion ``` ` blocks render as one-click "Commit suggestion" buttons (multi-line GA April 2020)
- Mermaid renders in PR review **body** (not reliable in line-comment threads — confine to walkthrough)
- PENDING review draft mode (`event` omitted) → user edits → `POST /reviews/{id}/events` to publish
- `GET /compare/{base}...{head}` for incremental delta reviews on subsequent pushes
- Body hard limit **65,536 chars**; cap line comments at **25** per review (industry norm)

Validated cost (500-LOC, 8-file PR, with prompt caching):
- Gemini 2.5 Flash: ~$0.04 / review (default)
- Claude Sonnet 4.5: ~$0.15 / review (Pro upgrade)

## Pricing & gating decision (open — needs user confirmation)

The user picked option **ii: "Free everything, monetise via BYOK / self-hosted licensing"**. There is one tension with current product policy:

- Today: `POST /reviews` (publishing any review to GitHub) is gated `requireTier('pro')` at [server/routes/repos/pulls.js:381](../../server/routes/repos/pulls.js#L381). The new "Publish AI Review to GitHub" flow goes through this same route.
- Three resolutions, ordered by my recommendation:

  1. **(recommended) Keep the gate as-is.** Generating and viewing the AI review in-app is free + BYOK; publishing to GitHub remains Pro. Aligns with existing policy, no migration risk, the WOW demo is fully free.
  2. **Drop the gate for AI-generated reviews only.** Free generation + free publish; manual reviews stay Pro. Adds a `source: 'ai-deep-review'` exemption check.
  3. **Drop the gate entirely.** Aligns 100% with "tudo free" but reverses an existing product policy decision — out of scope for this spec.

**Default for this spec:** option 1 unless the user reverses.

## Architecture

Three layers, kept independently testable.

### 1. Engine — `server/lib/ai-features/pr-deep-review.js` (new)

Sits next to the existing [pr-review.js](../../server/lib/ai-features/pr-review.js) which produces the lighter `overview / riskLevel / fileRisks / suggestedReviewOrder / estimatedReviewTime` summary. The new engine produces the **deep** structured review — walkthrough body + line comments + suggestions.

```js
// Pseudo-shape
{
  walkthrough: {
    summary: string,             // 1-3 paragraphs, markdown
    perFileTable: [               // posted as a markdown table in the body
      { path, change: 'added'|'modified'|'deleted', summary }
    ],
    mermaid?: string,             // optional sequence diagram, empty if not applicable
    estimatedReviewTime: string,
    riskLevel: 'low'|'medium'|'high'|'critical',
  },
  lineComments: [                 // capped at 25; overflow folded into walkthrough
    {
      path: string,
      side: 'LEFT'|'RIGHT',
      line: number,               // single-line anchor
      startLine?: number,         // multi-line anchor (optional)
      severity: 'info'|'suggestion'|'warning'|'critical',
      body: string,               // markdown
      suggestion?: string,        // raw replacement text — wrapped server-side in ```suggestion fence
    }
  ],
  modelUsed: string,              // 'gemini-2.5-flash' | 'claude-sonnet-4-5'
  inputTokens: number,
  outputTokens: number,
  costUSD: number,                // computed from server/lib/provider-pricing.js
}
```

**Provider strategy:**
- Default: existing Gemini provider (no env changes for current users)
- Opt-in: Anthropic when `ANTHROPIC_API_KEY` is set; user picks per-call via `provider` request param. Server-side selection: if user has BYOK both, prefer Anthropic Sonnet for Pro tier, else Gemini.
- Add `anthropicApiKey` + `anthropicModel` (default `claude-sonnet-4-5`) to [server/config.js](../../server/config.js) zod schema.
- New file `server/lib/ai-providers/anthropic.js` exposing the same `provider.generate({ parts, schema, generationConfig })` shape the existing engine uses, so [pr-review.js](../../server/lib/ai-features/pr-review.js) and the new engine can both swap providers transparently.
- Use Anthropic prompt caching (`cache_control: { type: 'ephemeral' }`) on the system prompt + repo context to amortise the ~70% prefix on incremental reviews.

**Sanitisation:** reuse `sanitizeForPrompt` from [server/lib/ai-features/sanitize.js](../../server/lib/ai-features/sanitize.js). Cap each suggestion at 4096 chars; reject any suggestion that contains backticks-of-7+ (defence against fence escape).

**Incremental review:**
- Read `last_reviewed_sha` from new `ai_pr_reviews` table (see Storage)
- If absent → full review of `base...head`
- If present and current `head_sha === last_reviewed_sha` → return cached `draft_json` (no LLM call)
- If present and different → `GET /repos/{o}/{r}/compare/{last_sha}...{head}`. On 422 (force-push, unreachable SHA) → fall back to full review and log a `forcePushFallback` counter.

### 2. Storage — new SQLite table `ai_pr_reviews`

```sql
CREATE TABLE ai_pr_reviews (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL,
  repo_owner TEXT NOT NULL,
  repo_name TEXT NOT NULL,
  pr_number INTEGER NOT NULL,
  last_reviewed_sha TEXT NOT NULL,
  draft_json TEXT NOT NULL,         -- the full DeepReview JSON above
  status TEXT NOT NULL,             -- 'draft' | 'published' | 'dismissed'
  github_review_id INTEGER,         -- set after publish, for follow-up edits
  cost_usd REAL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  UNIQUE(user_id, repo_owner, repo_name, pr_number)
);
CREATE INDEX idx_ai_pr_reviews_lookup ON ai_pr_reviews(repo_owner, repo_name, pr_number);
```

Per-user uniqueness so two collaborators on the same app instance can each have their own draft. Migration goes in [server/db.js](../../server/db.js) following the existing pattern.

### 4. API endpoints (new)

All on `server/routes/ai/deep-review.js`:

| Method | Path | Purpose | Gate |
|---|---|---|---|
| `POST` | `/api/ai/deep-review/:owner/:repo/:pr` | Generate or refresh AI review (incremental-aware). Returns `{ draftId, draft }`. | requireAuth |
| `GET` | `/api/ai/deep-review/:owner/:repo/:pr` | Get current draft (fast — no LLM call). | requireAuth |
| `PATCH` | `/api/ai/deep-review/:draftId/comments/:commentId` | Edit / accept / dismiss a single AI comment. | requireAuth |
| `POST` | `/api/ai/deep-review/:draftId/publish` | Publish to GitHub via existing `POST /reviews` machinery. | requireAuth + (see gating decision above) |
| `DELETE` | `/api/ai/deep-review/:draftId` | Discard draft. | requireAuth |

Generation is wrapped in `gh-outbox.enqueueAndExecute` for retry. Reads use `gh-cache.readThrough` per the project pattern (memory: `project_resilient_pr_issue_commit`).

## GitHub publish flow (the critical detail)

```
┌───────────────────────────────────────────────────────────────────┐
│ User clicks "Publish to GitHub →"                                 │
├───────────────────────────────────────────────────────────────────┤
│ 1. Frontend: open PublishReviewModal, render server-side preview  │
│    (Markdown rendered, mermaid rendered, suggestion blocks shown) │
├───────────────────────────────────────────────────────────────────┤
│ 2. User confirms event (Comment / Approve / Request changes) and  │
│    optional review summary additions, clicks Publish              │
├───────────────────────────────────────────────────────────────────┤
│ 3. Server builds the single batched payload:                      │
│      {                                                            │
│        commit_id: state.headSha,                                  │
│        body: walkthroughBody + footer,                            │
│        event: 'COMMENT' | 'APPROVE' | 'REQUEST_CHANGES',          │
│        comments: [                                                │
│          {                                                        │
│            path, line, side, start_line?, start_side?,            │
│            body: cmt.body + (cmt.suggestion                       │
│              ? '\n\n```suggestion\n' + cmt.suggestion + '\n```'   │
│              : '')                                                │
│          }, ...                                                   │
│        ]                                                          │
│      }                                                            │
├───────────────────────────────────────────────────────────────────┤
│ 4. POST to GitHub. On 422 (stale commit_id) → re-fetch head_sha,  │
│    re-anchor line numbers via diff hunks, retry once.             │
├───────────────────────────────────────────────────────────────────┤
│ 5. On success: persist github_review_id, mark draft 'published',  │
│    invalidate gh-cache for the PR, surface toast with link.       │
└───────────────────────────────────────────────────────────────────┘
```

**Footer (always appended to walkthrough body):**

```markdown
---
> 🤖 _Generated by GitHub Repo Manager · reviewed and published by @<user>_
> _Model: `claude-sonnet-4-5` · Cost: $0.13 · Incremental from `<sha7>`_
```

This satisfies the "label AI-generated content" disclosure norm. **GitHub App identity (proper `[bot]` user) is deferred to slice 4** — the 3–5-day side quest is not worth blocking the launch.

## Force-push & staleness handling

Three failure modes, all handled defensively:
1. **Force-push invalidates `last_reviewed_sha`** → `compare` returns 422 → fall back to full review of `base...head`. Counter logged for observability.
2. **Head moved between draft generation and publish** → publish endpoint compares `state.headSha` against current PR head. If different, return 409 with new head — frontend re-anchors comments via the existing `useReviewData.checkStaleness` flow already in [PRReviewView.jsx:181](../../src/components/PRReview/PRReviewView.jsx#L181).
3. **Line numbers drift due to intermediate commit** → re-anchor by matching the original suggestion's line content against the current file. If no match in ±5 lines → drop the comment with a "Skipped (file changed)" toast item.

## Security considerations

- Sanitise every LLM input via existing `sanitizeForPrompt` (cap diff chunks at 80kB)
- Reject AI-generated comments whose `body` contains the literal string ` ``` ` more than 6 times (fence escape attack)
- Rate limit `POST /api/ai/deep-review/:owner/:repo/:pr` per user: 30 generations/hour (configurable via `AI_DEEP_REVIEW_RPH`)
- Body length cap: walkthrough body ≤ 50,000 chars before footer; truncate with `...[truncated]` and log
- All SQL via parameterised queries (existing project rule)
- BYOK API keys remain encrypted via the existing `credentialEncryptionKey` machinery

## Success criteria

1. User opens a PR, clicks "Generate AI Review" → receives walkthrough + ≤25 line comments + per-file table in <15s on a 500-LOC PR (Gemini Flash)
2. Walkthrough body renders Mermaid sequence diagram inline in the right panel
3. Each AI comment can be Accepted / Edited / Dismissed; counts update live
4. Clicking "Publish to GitHub" produces a single PR review on github.com containing the walkthrough + accepted comments + working "Commit suggestion" buttons
5. Re-clicking "Generate" after a new push produces a delta review (only new comments) in <50% of the original time
6. Force-push triggers full re-review (not 500 error)
7. Stale-head publish is detected and surfaces re-anchoring UX (no silent failure)
8. Footer with "Generated by GitHub Repo Manager" appears on every published review
9. Free user with Gemini BYOK can generate + view AI review (publish gating per pricing decision above)
10. Zero new console errors in MOCK_MODE; all e2e tests pass; bundle budget gate doesn't fail
11. Anthropic provider works alongside Gemini without env-var changes for users who don't set it
